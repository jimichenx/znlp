# 分词模块审查

审查范围：`dev.znlp.segment` 及默认入口 `Znlp.segmenter()`。  
审查方式：按流水线模块对照源码，区分「会改切分结果的逻辑错误」和「数据/设计缺口」。

文中的插件总线是当时的组装方式。当前默认是 `Znlp.segmenter()` = `SegmentRecipe.standard()`：词典、二元 Viterbi、人名、词性。NER、用户词典、纠错、感知机不在这条路上。

---

## 1. 入口与流水线

涉及：`Znlp`、`PipelineSegmenter`、`PipelineSegmenterBuilder`、`SegmentModule`。

### 1.1 单字符短路（P1）

`PipelineSegmenter.handleBoundaryCases` 在 `text.length == 1` 时直接吐一个 `Nature.x`/`w` 的 Token，不建词图、不跑插件。

后果：`"的"`、`"我"` 不会走核心词典，也没有词频和真实词性。`segment(String)` 对空串返回空列表，对单字走这条捷径，行为不一致。

### 1.2 `segment(char[])` 原地改写（P2）

若配置了 `CharNormalize`，会直接改调用方传入的 `char[]`。`segment(String)` 内部 `toCharArray()` 无此问题；对外 `char[]` API 会破坏入参。

### 1.3 切分算法忽略 `isEnabled()`（P3）

后处理器会检查 `processor.isEnabled()`，`WordSplitAlgorithm.fill()` 不会。禁用原子识别/人名切分算法不会生效。

### 1.4 默认分词器没有词性（P2，过时）

审查时 `Znlp.segmenter()` 只有二元语法和人名，除人名、原子词外 `Token.nature` 多为 `null`。配方重构之后，`segment()` / `segmenter()` 绑定 `SegmentRecipe.standard()`，包含感知机词性。NER、用户词典、纠错和感知机分词仍要显式写在配方上。README 与 `docs/设计架构/分词.md` 与此一致。

### 1.5 `ViterbiBestPathAlgorithm` 未注册为单例（P3）

每次 `getService` 都自动 new。功能正确，只是重复构造平滑常量表。

## 2. 词图（Wordnet / Vertex / Wordpath）

### 2.1 起始节点词性（P0，已修）

`VertexHelper.newBegin()` 曾使用 `Nature.newWord`。`nature2id(newWord)` 返回 `-1`，起始节点 `wordID=-1`、`freq=0`，Viterbi 无法查 `0Begin → 首词`。

现已改为 `Nature.begin`。结束节点本来就是 `Nature.end`，无此问题。

### 2.2 `Vertex` 拷贝丢失词频（P2）

```java
public Vertex(Vertex node) {
    this.length = node.length;
    this.wordID = node.wordID;
    // 未复制 freq、nature
}
```

`Wordnet.subWordnet()` 用 `getOrCrete(length)` 只保留长度，子图上的 Viterbi 几乎只靠平滑项。

### 2.3 `Wordnet.indexAt` 无越界保护（P3）

`sindex` 不是 `-1` 或 `charSize` 时直接 `slotList[sindex]`。词图不完整时 Viterbi 的 `row(i + node.length)` 可能越界。正常词典图一般碰不到。

### 2.4 `fillNill`（可接受）

空行补 `length=1, freq=1`、无 `wordID`。只覆盖「该位置没有任何词」的洞，词典里的单字应由 DAT 匹配补上。逻辑正确。

### 2.5 `willCutOtherWords`（可接受，边界弱）

只检查合并跨度的左右边界是否已是切分点，不检查内部。这是有意设计：允许把 `南京/市` 合成 `南京市`。注释里的 TODO 仍然在。

## 3. 核心词典

涉及：`CoreDictionaryFactory`、`CoreDictionarySplitAlgorithm`、`CoreDictionaryImpl`。

### 3.1 切分本身（通过）

`CoreDictionarySplitAlgorithm` 用 DAT 全匹配，顶点带 `wordID` 和词频，与 bigram 的 ID 空间一致。`你→好 = 94` 已实测。

### 3.2 `totalFreq` 未计入补齐标签（P3）

`ensureAllLabelsPresent` 在算完 `totalFreq` 之后才插入 `\u00010Begin` 等 10 个标签。最多差 10，对平滑影响可忽略。

### 3.3 词条缺口（P2，数据）

`CoreDict.txt` 无「长江大桥」。词典路径最多切成 `南京市/长江/大桥`，不会出现 `南京市/长江大桥`。

---

## 4. 二元语法与 Viterbi

涉及：`BigramPlugin`、`BiGramTableDictionaryFactory`、`ViterbiBestPathAlgorithm`。

### 4.1 加载 `trim()`（P0，已修）

抽象词 key 为 `\u00010Begin`。`String.trim()` 会去掉 `\u0001`，整段句首二元（约 9k 对）被跳过。  
已改为只剥行尾空白；缓存前缀改为 `BiGramTable_v2_`，旧缓存会失效重建。

实测：`\u00010Begin → 慰问信 = 6`。

### 4.2 Viterbi 已接入，但本句搭配为 0（P2，数据）

算法确实用 `bigramFrequency(from.wordID, to.wordID)`。对本句：

| 搭配 | 频次 |
| :--- | ---: |
| 南京 → 市长 | 0 |
| 南京市 → 长江 | 0 |
| 长江 → 大桥 | 0 |
| 江 → 大桥 | 7 |

`南京`、`南京市`、`长江` 在 `CoreDict.bigram.txt` 中不是 first-word。无共现时退回一元词频，观感上像「只用了词典」。

自定义词 `wordID < 0` 时强制选中的逻辑被注释掉，用户词只能靠后处理合并。

### 4.3 权重公式（可接受）

沿用 HanLP：越小越好。`value < 0` 再取反是防御性处理。未登录词 `freq==0` 当成 1，避免除零。

## 5. 原子识别

涉及：`AtomSplitAlgorithm`、`AtomRecognizer`。

### 5.1 `put` 覆盖词典节点（P1）

```java
wordnet.put(result.getOffset(), result.getLength())
        .setAbsWordNatureAndFreq(nature);
```

`VertexRow.put` 对相同 `length` 是替换。数字/时间若与词典词同跨度，会丢掉原 `wordID/freq`，改成抽象词 ID（`m`/`t` 等）。Viterbi 之后走的是抽象词 bigram，不是原词。

更稳妥：已有节点则只补 `nature`，或 `getOrCreate` 后按需更新。

### 5.2 `@` 检测死代码（P3）

`foundAt` 声明后从未赋值，循环也不识别 `@`。纯邮箱仍会因字母走完整扫描，功能上大多没问题。

---

## 6. 人名识别

涉及：`PersonNamePlugin`、`PersonNameAlgorithm`、`PersonNameProcessor`。

### 6.1 三人名切开词典词（P0，已修）

默认切「南京市长江大桥」曾得到 `[南京市, 长, 江大桥]`：感知机把「江大桥」当三人名写入词图，默认频次 10000，Viterbi 压过「长江/大桥」。

已在 `PersonNameAlgorithm` 跳过「会切开更早位置、长度≥2 词典词」的人名。当前默认结果：`[南京市, 长江, 大桥]`。

### 6.2 Processor 对 ≤3 字人名不强制合并（P2）

`PersonNameProcessor` 遇到已有 `nature==nr` 的顶点直接 `continue`，不调用 `combine`。若 Viterbi 没选这条边，后处理也不会拉回来。≤3 字完全依赖词图阶段的高词频竞争，误伤（江大桥）和漏召（陈宝被竞品压过）都可能发生。

---

## 7. 感知机分词（CWS）

涉及：`CwsPlugin`、`CwsSplitAlgorithm`、`CwsPerceptron`。

### 7.1 未登录词 `Nature.newWord` 无效（P1）

```java
vertex.setAbsWordNatureAndFreq(Nature.newWord);
```

`nature2id(newWord)` 为 `-1`，词性、词频都不会写上。OOV 顶点保持 `wordID=-1, freq=0, nature=null`。随后 Viterbi 当 `freq=1` 处理，且无法走抽象词 bigram。

应直接 `vertex.nature = Nature.newWord` 并设一个合理 `freq`，不要走 `setAbsWordNatureAndFreq`。

### 7.2 插件仍用词典 Viterbi（设计）

`CwsPlugin` 的最优路径仍是 `ViterbiBestPathAlgorithm`。词图里主要是感知机给出的词，再加原子和 `fillNill`。CWS 是候选生成器，最终仍可能被二元/一元改写。若期望「感知机说了算」，需要线性路径算法或把 CWS 词权重大幅抬高。

---

## 8. 自定义词典

涉及：`UserDictionaryPlugin`、`UserDictionaryProcessor`。

### 8.1 已存在顶点时不合并路径（P1，已修）

旧实现在词图里已经有同跨度顶点时跳过 `combine`。词即使已经在核心词典里，Viterbi 切碎之后用户词典也无法合并。

配方重构之后，`UserDictionaryProcessor` 只要 `canForce` 通过就 `force`，不再看词图里有没有这个节点。当前契约是：用户词两端落在已有路径边界上就合并；一端卡在别的词中间则不动。`南京市 / 长江 / 大桥` 加上用户词「长江大桥」会合并；用户词「市长」不会切开「南京市」。`UserDictionaryPluginTest` 锁住这两种结果。

插件 JavaDoc 仍写 `CustomDictionaryPlugin`，与类名不一致（P3）。

---

## 9. 纠错

涉及：`CorrectionPlugin`、`CorrectionWordpathProcessor`、`DefaultCorrectionDictionary`。

### 9.1 插件装不上处理器（P0）

```java
public Set<Class<? extends WordpathProcessor>> getProcessorTypes() {
    if (dictionary != null) {
        return Set.of();          // 有词典 → 不声明类型
    } else {
        return Set.of(CorrectionWordpathProcessor.class); // 没词典 → 走 DI
    }
}
```

未覆盖 `getProcessors()`。因此：

- `new CorrectionPlugin(dict)`：类型为空、实例也为空，**插件等于没装**。
- `new CorrectionPlugin()`：DI 解析 `CorrectionWordpathProcessor(CorrectionDictionary)`，而 `SegmentModule` 没有注册该接口，构建容易失败。

正确做法：有词典时 `getProcessors()` 返回 `new CorrectionWordpathProcessor(dictionary)`；无词典再走类型 + 工厂。

### 9.2 资源不存在（P2）

默认路径 `correction-dict/correction_dict.txt`，仓库中无此文件，也未加 `znlp/` 前缀。即使 DI 成功，加载也会空跑。

## 10. 词性（POS）

涉及：`PosPlugin`、`PosPerceptronProcessor`。

默认分词器未安装，见 §1.4。

处理器逻辑大体合理：词典词性优先，`newWord`/`nr` 可被模型覆盖；`nr` 且长度>3 且原先无词性时降为 `n`，用来压「基础设施/nr」这类误标。

依赖：若 CWS/词典没把 `Nature.newWord` 写上（§7.1），「可被覆盖」的分支实际上走不到。

---

## 11. NER

涉及：`NerPlugin`、`NerProcessor`。

`NerPlugin` 会在缺少 POS 时自动 `installPlugin(PosPlugin)`，顺序 POS=LEVEL4、NER=LEVEL5，依赖方向正确。

### 11.1 单字实体 `S-` 被丢（P1）

```java
if ("O".equals(tag) || "S".equals(tag)) {
    from = -1;
    length = 0;
}
```

`S-ns` / `S-nt` 与 `O` 同等处理，单 Token 地名/机构不会改词性，也不会合并。应把 `S-*` 直接标到当前顶点。

`B-`/`M-`/`E-` 不完整时（有 E 无 B）靠 `from != -1` 保护，可接受。异常只打日志，不中断分词。

---

## 12. 规则分词

涉及：`RuleBasedWordSplitAlgorithm`、`RuleSegmenterPlugin`。

规则命中后把 `freq` 抬到 `1000000 + priority`，并保留已有 `wordID`（若顶点已存在）。这比原子识别的「整节点替换」更合理，Viterbi 更容易选中 URL/Email 等。

`wordID` 仍为 `-1` 的新建规则词，二元贡献为 0，全靠超高词频，设计可接受。

整句 `new String(char[])` 再跑正则，长文本有多余拷贝（P3）。

---

## 13. 结果收集

涉及：`SimpleWordTermCollector`、`SentenceCollector`、`SmartSubwordComputer`。

默认是 `SimpleWordTermCollector`，不做子词。

`SmartSubwordComputer` 对 `term.length()>2` 建 `subWordnet` 再跑 Viterbi。因子图没有 `wordID/freq`（§2.2），三字是否拆开只能再回原图查 `wordID`。原图若被原子识别覆盖（§5.1），这里的 bigram 判断也会失真。

`SentenceCollector` 会丢掉纯空白 Token；`SimpleWordTermCollector` 不会。两种收集器空白行为不一致（P3）。

## 15. 建议修复顺序

1. **纠错插件**：`getProcessors()` 真正挂上 `CorrectionWordpathProcessor`；修正无词典时的 DI 注册。
2. **自定义词典**：`!willCutOtherWords` 时一律 `combine`。已由配方重构完成，见 §8.1。
3. **原子识别**：同跨度已有词典节点时不要 `put` 替换。
4. **CWS**：OOV 直接设 `Nature.newWord` 和词频，不要走 `setAbsWordNatureAndFreq`。
5. **NER**：处理 `S-*`。
6. **单字符**：走完整流水线，或至少查一下核心词典。
7. **数据**（可选）：核心词典补「长江大桥」，二元表补 `南京市→长江` / `长江→大桥` 等，演示句才能切成 `南京市/长江大桥`。

当前默认 `Znlp.segmentToStrings("南京市长江大桥")` 为 `[南京市, 长江, 大桥]`。这是现有词典 + 二元表下的合理结果，不是最长匹配，也不是感知机分词。
